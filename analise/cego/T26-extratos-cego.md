# Reagrupamento cego de achados — T26-extratos

Você recebe 112 achados de uma crítica arquitetural. Cada um tem um id anônimo, o
módulo onde ocorre, a severidade e uma descrição de uma linha.

**Sua tarefa:** agrupar os achados que apontam o MESMO DEFEITO.

Atenção a defeitos **replicados**: quando dois módulos são implementações irmãs do
mesmo contrato, o mesmo defeito pode aparecer em ambos. Se uma única correção na
abstração compartilhada resolveria os dois, é o mesmo defeito.

**Critério, e é o único que vale:**

> Dois achados são o mesmo defeito quando apontam o mesmo problema no mesmo local,
> com a mesma causa raiz. Regra operacional: **se corrigir um resolveria
> automaticamente o outro, é o mesmo defeito.** Se cada um exige uma correção
> própria, são defeitos distintos — mesmo que estejam no mesmo módulo e sejam
> parecidos.

**Viés conservador, obrigatório:** na dúvida, **NÃO** agrupe. Agrupar a mais é o erro
mais caro aqui.

Não explique, não comente, não reordene. Responda **só** com este JSON:

```json
{"grupos": [["F-03", "F-07"], ["F-11", "F-02", "F-19"]]}
```

Cada lista interna é um grupo de achados que são o mesmo defeito. Achados que não
são duplicata de nenhum outro **não aparecem** — grupos de um só elemento são
implícitos. Se nenhum achado for duplicata de outro, responda `{"grupos": []}`.

## Achados

| id | módulo | severidade | descrição |
|---|---|---|---|
| F-01 | store | 🟡 | `candidatos_por_bloco(chave)` traz a estratégia de blocking para dentro do contrato de persistência. O módulo que V(2) reduziu a "só persistência" volta a conhecer o algoritmo de matching — a fronteira que a iteração 1 pediu foi restabelecida em prosa e desfeita no contrato. |
| F-02 | matcher | 🔴 | Um único módulo serve dois clientes com semânticas distintas: dedup compara transação × transação (mesma natureza, chave por identidade/valor) e reconcile compara transação × lançamento (naturezas diferentes, campos diferentes, pesos diferentes). O contrato `score(par) -> float` é genérico demais para estar correto nos dois — ou o módulo viola SRP, ou um dos dois usos vai receber um score sem significado. |
| F-03 | store | 🟡 | `migrar()` não declara transação nem ponto de restauração: falha no meio deixa a base contábil num esquema intermediário que nenhuma versão do software sabe ler. |
| F-04 | reconcile-engine | 🟡 | Se a resolução de IMP-01 for o casamento ótimo global (húngaro), o custo é O(n³) e inviabiliza VAL-4 mesmo com blocking. A escolha algorítmica em aberto tem consequência assintótica, não só de corretude. |
| F-05 | matcher | 🟡 | `MetricasBloco` é devolvida pelo contrato, mas nenhum módulo declara consumi-la ou persisti-la. A métrica que detectaria o bloco degenerado é produzida e descartada. |
| F-06 | reporter | 🟢 | o relatório não registra os parâmetros efetivos (limiar, janela, tolerância) daquela execução. |
| F-07 | dedup-engine | 🟡 | `DecisaoDedup` carrega camada e evidência, mas nenhum contrato declara que isso é PERSISTIDO. Se a evidência vive só em memória, um falso positivo descoberto no fechamento seguinte é inauditável — e VAL-2 exige zero falso positivo, o que pressupõe poder investigar um. |
| F-08 | matcher | 🟡 | As faixas 95 / 85 / 70 (P3-P5) vêm de blog de fornecedor, não de literatura revisada por pares — a própria spec registra a ressalva e ainda assim adota como default. Nada no design prevê calibrar esses cortes contra o ground truth antes de usá-los para decidir fusão. |
| F-09 | matcher | 🟡 | `score(par) -> float` não declara escala nem direção: 0-1 ou 0-100, maior é mais parecido ou é distância. Os parâmetros P3-P5 falam em 95/85/70. Um implementador que devolva distância normalizada 0-1 satisfaz o contrato e inverte todas as decisões de fusão. |
| F-10 | domain-model | 🟡 | `Dinheiro(valor, escala)` passou a guardar a escala original, mas nada declara que a igualdade é pelo valor numérico e não pela representação. `1250.00` vindo do CSV e `1250.000` vindo do OFX seriam o mesmo evento e comparariam desiguais. |
| F-11 | repository | 🟡 | `ResultadoImport` não tem forma declarada, mas o UC-1 exige que a CLI reporte novas / duplicatas-reimportação / duplicatas-cross-source / pendências. O contrato entre repository e cli está incompleto exatamente onde o caso de uso é verificado. |
| F-12 | audit-log | 🟡 | Sendo append-only, a trilha não pode ser corrigida se uma migração gravar registros errados — o mecanismo que garante integridade impede o reparo. |
| F-13 | reconcile-engine | 🟡 | Assume que existe no máximo um lançamento correspondente por transação (I4). A Fase 0 admite explicitamente que 1:N ocorre e deve virar pendência — mas o contrato `conciliar` não declara COMO o caso N é detectado antes de escolher o par 1:1. |
| F-14 | repository | 🟡 | Nenhuma entidade tem proveniência declarada: a linha gravada não aponta para o arquivo e a fonte que a originaram. Com várias contas e vários exports, é impossível atribuir uma transação ao seu arquivo de origem para conferência. |
| F-15 | review-queue | 🟡 | `resolver(id, acao)` não tem desfazer. Por I7 a decisão humana é soberana e não sobrescrita — logo um erro de digitação do analista vira permanente por design. |
| F-16 | matcher | 🟡 | O teto de bloco é um controlador sem histerese: perto do limite, um item a mais ou a menos muda a chave de bloco e reclassifica pares entre execuções consecutivas sobre dados quase idênticos. |
| F-17 | csv-adapter | 🟡 | Idem para linha com valor não parseável: sem quarentena de linhas rejeitadas, ou o lote inteiro se perde, ou as linhas somem silenciosamente — e o analista concilia sobre dados incompletos sem saber. |
| F-18 | ofx-adapter | 🔴 | OFXv2 é XML. Se o parser resolver entidades externas, um arquivo de extrato hostil executa XXE (exfiltração de arquivo local) ou expansão exponencial de entidades. O arquivo é entrada não confiável por definição — o adapter não declara desabilitar resolução de entidades. |
| F-19 | matcher | 🟡 | O custo de similaridade é pago sobre candidatos acumulados de todos os períodos. Sem janela de comparação declarada, o trabalho gasto cresce sem que o valor entregue cresça: duplicata de reimportação de 3 anos atrás é praticamente impossível. |
| F-20 | audit-log | 🟡 | `historico(chave) -> [Evento]` não declara o que é `chave` — identidade de observação, chave de evento, ou par de itens. As três dão históricos diferentes para a mesma pergunta do auditor. |
| F-21 | canonicalizer | 🟡 | "Descrição normalizada" não tem regra especificada: caixa, acentos, pontuação, espaços múltiplos, abreviaturas. Duas implementações corretas do contrato geram hashes canônicos diferentes para a mesma transação, e L2 deixa de funcionar entre versões do próprio sistema. |
| F-22 | domain-model | 🔴 | `regra_normalizacao() -> Regra` é versionada, mas mudar a regra invalida toda `ChaveEvento` já gravada e nenhum caminho de reindexação está declarado. Na primeira correção da regra de normalização, o histórico inteiro deixa de casar consigo mesmo. |
| F-23 | reporter | 🟡 | `render(relatorio, formato)` não enumera os formatos suportados nem define o padrão. O relatório é o entregável que o analista consome; seu formato não está especificado. |
| F-24 | matcher | 🔴 | Bloco degenerado: milhares de tarifas de mesmo valor redondo (R$ 30,00) caem na mesma chave `(abs(valor), janela)`.
